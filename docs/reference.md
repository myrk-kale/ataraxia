# Reference

The details behind the [README](../README.md): what each part does, how it is built, the shortcuts and
the choices that are easy to miss.

## What is in it

- **Chat:** OpenCode (ACP), Cursor (ACP, `cursor-agent acp`), Claude Code (stream-json) and Codex (app-server) through one agent host. Cursor shares the ACP engine with OpenCode and adds the questions (`cursor/ask_question`) and plans (`cursor/create_plan`) Cursor asks for; sign in once with `cursor-agent login`, and `ATARAXIA_CURSOR_BIN` points at a CLI that is not on the `PATH`. Streaming, tool cards, permissions, cancel, persisted transcript and persisted subagent conversations. While the agent works you can keep writing: Enter (or the Queue button) adds the message to a queue shown above the composer, and the messages go out one after another as each turn ends well. Each queued message has "Send now", which stops the running turn and sends that message next, ahead of the rest, and a remove button, and the queue as a whole has Pause and Resume: a paused queue sends nothing by itself, not even after a `/compact` (which, left alone, lets the queue carry on once it finishes). A turn you stopped, or that failed, pauses the queue instead of carrying on; "Send now" resumes it. The queue lives in the app, not in the window, so it keeps going while you look at another chat, but it does not survive closing the app. Pictures can go with a message (images only for now: PNG, JPEG, GIF or WebP, up to 5 per message and 5 MB each): paste them into the message field or use the paperclip, and they show as thumbnails you can take back out. The app keeps each picture as a file of its own under its data folder, judged by its bytes and not its name, and the message shows it. Claude Code receives it as an image, Codex as a local image, and OpenCode is told the file's path in the text; deleting the chat deletes its pictures. Pictures can be queued with their message.
  Reasoning text streams in a collapsible Thinking section when the provider exposes it. Its availability depends on the harness and model; the transcript keeps it in order across restarts.

Agent profiles: a profile is a way of starting an agent, usually another account. Settings > Agent profiles keeps, per agent (Claude Code, Codex, OpenCode), a list of them beside the default, each with a name (unique per agent), a colour and a command. The command is written as in a terminal: leading `NAME=value` settings (usually the variable that points the agent at another account's folder: `CLAUDE_CONFIG_DIR` for Claude Code and `CODEX_HOME` for Codex), then optionally the program and its arguments; with no program the agent's usual one runs with those settings. Quotes and backslashes work as in a shell for the simple cases, `~` is your home folder, and nothing else is expanded (no `$VAR`, no pipes), so what is typed is what runs. The program is looked up the way the agents' own binaries are, so an app launched from the Dock finds it too. The form checks the command as you type (what it would run, or that the program was not found) before saving. The profile is chosen per chat, not for the whole app: the composer has a Profile picker next to the provider (shown once the agent has a profile), with Default and the agent's profiles; the settings only add, edit and delete them. A new chat starts with the profile last chosen for its agent, and a chat that was open before this existed kept the one that was in use. A chat notices at its next message that its profile changed, restarts its agent process under the new one (never during a turn) and points the new agent at a text record of the conversation, as when the agent is switched. A BTW or delegated helper runs under its chat's profile; switching a chat's agent resets its profile. A profile that cannot start (the program is gone) fails that message with the reason and leaves the running process alone. The profile a chat uses shows as a blur of its colour behind the agent's mark in the composer, with its name on hover and for screen readers, and the limits meter reads the numbers of that account: each profile keeps its own, and the details name the profile. Profiles live in the app's local preferences and are never sent anywhere; a deleted profile in use falls back to the default.

Every agent event leaves the app with a number, in the order they were sent, and the chat applies each number once: an event that reaches the window twice (a listener left over from a hot reload, say) is ignored the second time, so streamed text is never doubled. The stored conversation is built in the app from the events as they happen and does not depend on this.

A message you send shows at once, before the app has taken it in: it is put in the transcript as pending and the agent is shown as working, with the loader (three dots in a wave), and when the app reports the message (after it has marked the start of the turn with a git snapshot of each repository of the workspace) that report replaces the pending one in the same place under the same key, taking over its pictures from the ones already in hand so they do not flash. A message the app refuses is taken out again, the status goes back to what it was, and the text and pictures return to the field, ahead of anything typed since; a message the app has already taken in is never withdrawn. What goes to the queue is listed at once as being added (it cannot yet be sent or removed) and the queue's own entry replaces it. A second message sent while the first is still on its way waits for it, so they arrive in order.

Next to the agent's name in the composer, a small meter shows how much of the provider's subscription limits is spent: the five-hour window and the weekly one, each as a bar and a number (`5h ▬ 6%  Week ▬ 76%`). It is the meter of the provider the chat runs on, so it changes with the provider and a provider that reports no limits (OpenCode, the demo provider) shows none. Ataraxia measures nothing itself: Claude Code reports both windows after each message (its `rate_limit_event`), and Codex answers `account/rateLimits/read` when its process starts and pushes an update when the numbers change. Which window is which is read from the window's length, not its position, because a plan may have only the weekly one (a Codex team account reports a single 10080-minute window, and it shows as the weekly limit alone). The last report of each provider is kept in the preferences, so the numbers are there when the app opens, before any agent has spoken; a window whose end has passed since the report counts as reset and shows 0%, and the details say it is waiting for the next message. From 75% the number turns amber and from 90% red, and a warning icon goes with it, so the colour is never the only sign. Click it (or press Enter on it) for the details: each window's share, when it resets (as a countdown and as your own clock time), the plan if the provider names it, and how long ago the provider reported.

What is not on screen costs nothing. The transcript is cut into rows, one per message or tool call (a long turn of the agent is many rows, so it can be cut anywhere), and only the rows in view and a few either side are in the page, drawn by a windowing list (`@tanstack/react-virtual`); the rest are space. A row's height is measured the first time it is drawn and kept, and until then it is guessed from its text, code, tables and diagrams (within about 5% on the test chat), so the scroll bar and the position stay right as you scroll. A reader at the bottom stays at the bottom as the reply grows; one who scrolled up is not moved. A row is drawn again only when its own message changed, so a streaming reply redraws one row, not the chat. A tool call keeps its input and output out of the page until it is opened, and which ones were open is remembered; pictures read from the app are kept up to 32 MB, the least recently seen going first; the layout of a text diagram and the SVG drawn by the library are kept (up to 24 and 40) so that scrolling back shows them at once. One consequence: the browser's own find-in-page only sees the rows in the page.

Anything in a reply that is worth taking away has a Copy button (on hover or keyboard focus): a table copies as tab-separated cells and as an HTML table, a code block as its code, a diagram as its source. A fenced `mermaid` block is drawn as a diagram. A flowchart (`flowchart` or `graph`, in any direction, with square, round and decision nodes, plain, dotted and thick links, open links and link labels) is drawn as text on the graphics card: boxes and lines laid out in layers (a label longer than 40 characters, or any label when the chart would otherwise be too wide, is cut at spaces into several lines in a taller box, and a chain can be up to 40 steps deep), links routed round the boxes, and everything drawn with WebGL2 from a glyph atlas. The lines, corners and arrowheads are drawn from geometry, so they meet exactly at any size and on any screen, and the letters are set in the code font of the settings. The colours are the app's tokens, so the diagram follows the theme and redraws when it changes. All the diagrams on the page share one WebGL context, since a browser allows only a few. A `subgraph ... end` is drawn as a titled frame (rounded, dim, with the title in its top edge) round the nodes written inside it, and subgraphs can hold subgraphs. Each subgraph is laid out on its own and then placed as one block, so frames never overlap and what is inside a frame is exactly what was written inside it; a node belongs to the first subgraph it is written in, and mentioning it again later in a link does not move it. A `direction` inside a subgraph is honoured when no link joins what is inside to what is outside, and ignored otherwise, as Mermaid does. A link that crosses a frame runs over its edge, and keeps off the title and off frames it has no business in. The frames stay on screen while the animations draw what is inside them. The animation (data flow by default) repeats while the diagram is on screen and stops by itself when it scrolls away. A click on the diagram pauses it, and another click lets it go on (Enter and Space do the same for someone with no mouse, and a small "Paused" label says so); a paused diagram costs the page nothing, and stays paused when scrolled away and back. Each diagram has its own choice of animation in its toolbar (draw in, data flow, step by step, node pulse, typing, state changes, matrix glitch, or none), which starts as the setting. Settings > Appearance > Diagrams sets that default, whether it repeats (off plays it once as the diagram comes into view and then leaves it still) and the pieces the lines are made of (square, all rounded, double, heavy or plain ASCII); the system's reduced-motion setting turns the animation off. The toolbar, shown when the pointer is over the diagram or focus is in it, also has a button that opens the diagram full screen and a Copy button that copies the Mermaid source. Full screen takes up the window like an image: scroll or pinch to zoom about the pointer (or the buttons, or + and -), drag to move it (or the arrow keys), 0 or the Fit button to fit it to the window, a click to pause, Esc or Close to leave. It is drawn again at each zoom so it stays sharp, up to a limit the graphics card and the cost of the canvas set; some of the diagram always stays in the window. While it is open the keyboard belongs to it (Shift+arrows do not change space behind it, and Esc does not stop the agent), and focus goes back to the button that opened it. A diagram tells a screen reader what it shows (`Flowchart, left to right. Client to Gateway; ...`). The parser is strict: what it cannot draw faithfully (another kind of diagram, `A & B`, a link to a whole subgraph, an empty subgraph, subgraphs nested more than three deep or more than 16 of them, bidirectional links, a label with markup or in a wide script such as CJK or emoji, more than 60 nodes or 100 links, or a drawing that is still wider than 260 columns or taller than 420 rows after its labels were cut into lines of 22 characters) goes to the Mermaid library, which draws an SVG and is loaded only then (about 2 MB; the text drawing is about 22 KB), as does a machine without WebGL2. While a reply is still being written the code is shown and neither is started. In a long chat only the diagrams on screen exist.

A fenced `svg` block is drawn as the picture it holds, so the agent can explain with a concept map, a mind map or an architecture sketch. It is shown through an `<img>` (a data URL), which is an image document: nothing in it can run and nothing in it is fetched, and it is never put into the page itself, where its styles could reach the app. Before it is shown the drawing is checked (one well-formed `<svg>`, at most 300,000 characters, no `DOCTYPE` or entities) and made safe: scripts, event attributes, `<foreignObject>`, `<image>`, animation, links and any `url()` that leaves the drawing are removed, and a missing `xmlns` is added. It is sized from its `viewBox` (or its `width` and `height`; with neither it is not drawn), and the app's colours are put in a stylesheet ahead of the drawing's own: classes (`node`, `node-accent`, `edge`, `arrow`, `title`, `label`, `small`, `muted`, `accent`, `good`, `bad`, `warn`, `bg`) and variables (`--ink`, `--muted`, `--line`, `--tint`, `--panel`, `--accent`, `--accent-bg`, `--green`, `--red`, `--amber`), so a drawing follows the theme and is redrawn when it changes. The agent is taught how to draw one by the guide page `svg.md` (when a drawing earns its place, an 800-wide `viewBox`, the theme classes, a layout grid, text that fits, a mind map and a boxes-and-arrows example), which it reads before its first drawing of a chat; a diagram asked for with no kind is still a Mermaid one. The `<title>` and `<desc>` are the image's text alternative. The toolbar, shown on hover or keyboard focus, has Expand (the drawing larger, in a dialog), Code (the sanitised source, with a button back to the image) and Copy (that source). While the text is still arriving a "Drawing…" placeholder stands in for it, and if it never becomes a valid SVG the code is shown with the reason. A drawing counts as one diagram, not as lines of code, when the height of a reply is guessed before it is on screen.
- **Code:** Monaco (bundled, no CDN). A local switcher between Components, Changed files (one per line) and the Project tree. Components are built with tree-sitter and leave out anything inside a folder whose name starts with a dot (`.github`, `.claude`); the changed files and the project tree still list them (Rust, TypeScript/TSX, JavaScript/JSX, Python, Go and Java; other files count as one unit): every changed line is attributed to the function, method or type that contains it, and the queue is ranked by heuristics over the syntax tree and git, with no model involved. Each unit is scored from the contract it changes (public signature, removal), who can reach it (routes, commands, `main`, exports, mentions from other folders), sensitive areas in its path or name, complexity, risky constructs found in its body (SQL built from text, hard-coded secrets, shell and dynamic execution, disabled certificate checks, swallowed errors, unsafe blocks, I/O in loops), whether a test mentions it, and its size, minus formatting-only changes, tests and generated code. Every point is listed with its reason. `V` (or Ctrl/Cmd+Alt+V with the cursor in the editor) flips between the current and previous version in the same viewport (a new file has no previous one, a removed file has no current one), the current version of a file is the working tree and can be edited (an `*` after its name means unsaved changes, Ctrl/Cmd+S saves, and an outside change is a conflict, never overwritten), while the previous version is the past and read-only, and a branch or commit taken as the head is read-only too, and comments, approvals per file and checkpoints live next to the code.
- **Decisions:** an artifact of the chat, not a space. Once the agent recorded some, a collapsible Decisions row appears in the chat ("3 decisions to review"). Expand it to review the decisions in place. Each decision shows the choice, context, rationale, alternatives and code references. Pending decisions come first, with Approve and Reject actions. A rejection always needs a comment. When the last open decision gets its verdict, the main chat is sent one message: that everything was approved, or which decisions were rejected and the comment on each. A decision can be reopened, and its next verdict is reported again. Approve/reject is independent from reviewing the code.
- **Tasks:** a side panel like the artifacts, from its icon in the header or `Ctrl/Cmd+T`.
- **Memory:** what the agents remember, shared by every chat and every provider, as a graph (see "Memory" below). The graph opens from its icon in the header or `Ctrl/Cmd+Shift+G`; Settings > Memory switches it on or off and lists, edits, links and deletes what is kept.
- **Companion (pet):** a small animated character that floats over the interface, in every space, and says what the agents of all your chats are doing, the way the pets of OpenAI's Codex app do. One state at a time, the most pressing first: **needs you** (a chat waits for an approval or an answer), **error** (a turn ended badly), **done** (a turn finished well in a chat you have not opened since), **working**, or resting. Its speech bubble names the chat and opens it when pressed; a chat you are looking at is never "done" or "error". Drag it anywhere (it keeps its place as a share of the window, so it stays inside when the window is resized, and is remembered across runs), press it for a menu (open the chat, Customize, Mini, back to its corner, Hide), or focus it and move it with the arrow keys (Shift for bigger steps; Esc sends it back to its corner). Settings > Companion chooses Pet, Mini (only the status, as a pill) or Off; the species (drop, cat, bunny, robot, ghost, all drawn in code), colour, accessory (cap, glasses, bow, crown), name and size (60 to 200 %); or a picture of your own (PNG, WebP, JPEG or GIF up to 4 MB, made small and kept on this computer; an animated one becomes still); and previews how it moves in each state. `/pet` in a chat shows or hides it. With reduced motion in the system every state is a still picture. Settings are kept in the window's storage (`ataraxia.pet`). The built-in browser draws its pages as native views above the interface, so the pet is behind a page while the Browser space shows one.
- **Welcome tour:** the first start after the tour was added (everybody has no mark yet, so everybody sees it once) opens a dialog in the middle of the screen with everything else dimmed, after the opening animation. Ten slides, each with a screenshot of the app (the one for the theme in use) or a drawing, the problem it solves and two to four short points, with the keys worth knowing: the flow of a session, chat, the review queue, decisions, Flow, BTW, the browser, memory and tasks, and themes and shortcuts. Left and right arrows move, the dots jump, Skip or the last button closes it, and a click outside does not. It is remembered in the window's storage with a version number (`ataraxia.onboarding.seen`), so a rewritten tour can be shown again; the keyboard shortcuts dialog has "Replay the welcome tour".
- **Browser:** a space with a minimal browser built on the system's own webviews (WebKit on macOS): tabs, an address bar that also searches, back, forward, reload and stop, and a start page. `Ctrl/Cmd+Shift+L` opens it from anywhere (and goes back to the chat). The pages are native views drawn over a box in the middle of the space; a dialog, menu or list opened over it makes the page step aside, and a picture of it taken a moment before stands in. The Bug button opens developer tools under the page: a Console (logs and uncaught errors, filtered by level and text) and a Network list (the page's own fetch, XHR and WebSocket calls by default, files it loaded with one switch; click a request for its headers, bodies and where it came from, and copy it as cURL or `fetch`), both kept across navigations; "Inspector" opens the system's own inspector. **An agent can drive it** through eight `browser_*` tools of the `ataraxia` MCP server (`browser_tabs`, `browser_snapshot`, `browser_act`, `browser_screenshot`, `browser_eval`, `browser_console`, `browser_network`, `browser_inspect`), for any harness whose chat may write: it opens tabs, reads a page as text with a ref for each element, clicks, types, presses keys, selects, scrolls, drags and waits, taking several steps in one call, while a virtual mouse moves to each target with a caption so you can follow (and an edge glow shows the tab is being driven); it can take a picture of the page or of one element (no wider than 1280 px; macOS only for now), read the console and errors, list the page's requests with headers and bodies (find the call behind a value on screen, see the shape of its JSON, turn it into a `curl` or `fetch`, export a HAR), and inspect an element, storage, cookies and timings. Every action ends with what changed in the page (a new address, new errors, failed requests). Safety: the tabs an agent opens use a store of cookies of their own, apart from yours, and a tab of yours is its only when you press Share on it; the menu has a switch that shuts agents out altogether, "Take over" stops one at work, an agent can only open http and https addresses, credentials in headers, cookies and storage are hidden from it unless it asks to reveal them, and a page can never reach the app's own commands or its development server. The guide has `browser.md`, `browser-network.md` (automate through the HTTP calls a page makes instead of clicking) and `browser-debug.md` (debug a web app from its console, requests and elements). In a debug build, `ATARAXIA_DEBUG_API_FILE=<path>` writes the local API's address and a token there, so the tools can be driven with `curl` against `/mcp` while the app runs. Pages' events are synthetic (not trusted), which nearly every page treats as real.

- **Flow:** React Flow canvas with prompt presets (select, add, edit). Editing a preset never generates; only Generate does, with optional per-run instructions. Nodes point at files that exist and the diagram says when it is out of date. A diagram, like a decision, is about the conversation and not about a diff, so the agent can record one in a chat that has not changed any code (it hangs off an empty checkpoint of the code as it stands); only the parts that compare code, the review queue and the generation of decisions from a change, need a change to look at.
- **Autocomplete:** in the message field, a grey suggestion follows the caret: the rest of the word being typed, a phrase (the words you usually write next, stopping where your sentences usually stop) or a name from the code (the functions, classes and types the syntax analyzer finds in the chat's repositories). Tab or the right arrow accepts it, Esc dismisses it. It is built from three things: packaged word lists of the languages you choose (the 20,000 most frequent words of English, Portuguese for Brazil and for Portugal, Spanish, French, German and Italian, under `src-tauri/dictionaries`, from FrequencyWords, CC BY-SA 4.0), a word n-gram language model (up to three words of context, interpolated with absolute discounting) that learns from every message you send, in general and per chat, and is stored in the app's database so it survives a restart, and the code names. Only your own messages are learned: never what an agent writes, code blocks, paths, links or anything that looks like a key. Settings > Autocomplete turns it off, picks up to two languages (the system's language and English by default), turns phrases, code names and learning off separately, and forgets what was learned.
- **BTW:** `Ctrl/Cmd+K` opens a wide bar (`Ctrl/Cmd+Shift+K` opens a private one, with an accent border, whose replies never reach the main chat; it may edit files and run commands by default, the pencil makes a question read-only, and it always runs on the worktree and branch on screen) in the manner of Spotlight, from any space, with no button anywhere to summon it. The bar holds only its placeholder and, joined to its rounded body, a select to choose which provider and model run the question (the provider and model the chat is on right now by default, following it when it changes, until you pick one yourself, which is then kept). The answer appears below the bar. It never edits files. Selecting text in the Code editor shows a small bar next to it (Ask, Comment where a comment can be attached, Copy), after the pointer is released and the selection has settled: Ask opens BTW with the selection already attached, and the bar says so (`Selection · path:lines · N lines`); the agent is told that the user has that text selected in that file and those lines, so "this" and "here" mean it. What BTW is about is fixed when it opens. It knows what you have open in every space, whichever one you summoned it from: the selection, the component or the file in Code, the decision in Decisions, the diagram and node in Flow. Called from the chat, it is a fork of that conversation: it starts from what the main chat has said so far. Every BTW is also one of the chat's subagents: it is listed with the others, with its own conversation (you can write to it from there), and after every completed interaction Ataraxia adds a short summary of the latest question and answer to the main chat queue. The summary is marked as a parallel BTW update, not a new user message or authorization; if it suggests an action, the main agent only answers that it understood, and acts on it once the developer asks in the main chat. The full conversation stays in the BTW session, which remains available while the main agent works. It can also act inside Ataraxia, but only when you ask: comment on a component of the review queue (marked as the agent's), raise or lower a component's priority (with its reason, and a reset), and generate decisions or a diagram (optionally focused on something you say). The same works in the chat itself, where the agent does it through the local API (`POST /v1/comments`, `PUT /v1/priority`, `POST /v1/decisions`, `POST /v1/flows`, `POST /v1/decisions/{id}/commits`). BTW is provider-neutral: it ends its answer with a block that Ataraxia checks (the component must exist in the queue, a priority is 0 to 100) and applies, and the bar lists what was done and what could not be.
- **Scheduled messages:** an agent that has to come back to something later (a release or deploy still running, a retry in a few minutes) asks Ataraxia for it through the local API (`POST /v1/schedules` with `prompt` and `in_minutes` or `at`, optionally `every_minutes`; `GET /v1/schedules`; `DELETE /v1/schedules/{id}`), and the app sends it a message at that time, starting with `[Scheduled task <id>]`. It is the same for Claude Code, Codex and OpenCode, which is why Claude Code's own cron, wakeups and `/loop` are turned off (`CLAUDE_CODE_DISABLE_CRON=1`) while the local API is up. The app keeps the schedules per chat (so they survive a restart, a change of agent or a dead process) and a clock checks them every few seconds. A due message goes through the chat's own message queue: it waits for the agent to finish, goes out one at a time and holds when the user stopped the turn. A schedule that fell due while the chat's agent was not running (the app closed, the chat not opened yet) fires once when it runs again, not once per missed run; a recurring one is set to run again its interval after that, does not pile up behind itself in the queue, and expires after 7 days. The first run and the interval are 1 minute to 7 days; a chat holds up to 20. Above the message field a "Scheduled" strip lists them with their next time and an X to cancel, and a message sent by a schedule shows in the transcript as a "Scheduled" line instead of a bubble of the user. The agent reads `schedule.md` of the guide for this, only when it needs it. Separately from this, whatever the Claude Code CLI starts on its own (a wakeup it set before, the end of a command it left running) is shown as a turn of its own instead of being dropped.
- **Themes and fonts:** Settings has the theme and the mode. There are eleven themes (Ataraxia, Orca, Nord, Solarized, Gruvbox, Tokyo Night, Catppuccin, Rosé Pine, One, Everforest, GitHub), each with a light and a dark variant, and the mode is System, Light or Dark; you can also import any VS Code colour theme from its `.json` file, comments and trailing commas included (it has the one mode it was made in). The typeface and size of four areas are set there too: interface (the whole layout scales with it), chat and reading, code, and terminal. The typeface is a plain list of the faces this machine really has (detected, so a choice always shows), plus the bundled default. The built-in themes are small palettes read by the same importer (Orca's is the default theme of [stablyai/orca](https://github.com/stablyai/orca), MIT). A VS Code theme paints the interface, the editor and the terminal; every text colour is held to a contrast floor (4.5:1, 7:1 for the main text), so a theme made for an editor still reads in the panels around it. Code is coloured through Monaco's own tokenizer, mapped from the theme's TextMate scopes, so it follows the theme closely and not exactly (function names, for one, keep the variable colour). The chosen theme and fonts are applied before the first paint. The interface makes only a few small sounds: a light tick when you change space (the dots, `Shift + ↑/↓` or the wheel) or choose a model, effort, agent or provider, and a chime when the agent asks for approval. They are synthesised with the Web Audio API, so no audio file ships, and Settings > Sound turns them off or sets the volume. In Code, `Alt+Z` (or the button in the file header) wraps long lines or lets them run on, and is remembered.
- **Artifacts:** when a turn ends, a checkpoint (a snapshot commit of the working tree, no change to your branch or index) is recorded and the review queue is computed and the staleness of older diagrams is marked from runtime events, not prompts. Decisions are never extracted without a request. `Shift+A` lists them as chat → checkpoint → artifacts. Retries never duplicate an artifact, and work interrupted by closing the app is marked failed with a Retry. The drawer ends with "Delete all artifacts…", which removes the checkpoints of the chat and everything on them (queues, decisions and their threads, diagrams, marks, comments, priorities) after you type the chat's title, as when deleting a repository on GitHub; the chat, the code and git are untouched.
- **Branch and comparison:** the header has two selectors. The app follows git: a branch switched in a terminal, or a worktree added there, shows up in the app within a second, and the other way round. The branch selector lists every local branch of the repository (searchable, read from git each time it opens). Choosing one switches to it: a branch another worktree already has open selects that worktree, any other is checked out in the current one, never forced and never while an agent is working in it, and when git refuses (local edits in the way, for example) the notice carries git's own reason and nothing changes. Next to it, "Compare with" picks a reference, any other branch, remote branch, tag or recent commit, and that is all it does: Code then shows the current branch against it, as a pull request would (from the merge base, with the working tree as the head). The comparison is a checkpoint like any other, so marks, comments, decisions and the queue all work on it; with the working tree as the head you can edit, and "Compare again" re-reads it. The choice is remembered per chat, and "No comparison" goes back to the agent's turns. Nothing is compared by default: with no reference chosen, Code shows only what the agent changed in its last turn (or in a check you asked for with the refresh button), and when there is none it says so and asks you to pick a branch or a commit in "Compare with…" (a worktree on no branch, a detached HEAD, gets a line saying so). A comparison is never shown once it is no longer chosen. The files follow git too: a removal, checkout, stash or pull in a terminal, or a file made or deleted by another program, refreshes the Files tree, the open file and, when a reference is chosen, the Changed list, within a few seconds. This is a cheap look (the contents of `HEAD` and the index file every second, `git status` only when they moved and every few seconds otherwise, nothing while the window is hidden); a file open in the editor that disappears is marked removed, keeps its text and any unsaved edits, and can be written back. The last turn's list is a record and does not change with the files.
- **Workspaces:** a workspace is a named set of repositories. Opening a folder makes a workspace of one, so a lone repository looks exactly as it always did. "New workspace…" and "Edit this workspace…" in the workspace selector (the first segment of the header) take a name and the repositories that belong to it, and "Add folder…" brings in another one. The agent of every chat in a workspace can read and change all of its repositories: the chat starts in the repository in focus, the others are given to the agent as extra directories (Claude Code `--add-dir`, Codex writable roots, and for OpenCode the absolute paths named in its first message), and each chat keeps one worktree per repository, fixed when it is made (the one selected there, else the main checkout). The app still looks at one repository at a time: from two members on, a repository selector follows the workspace selector in the header and tops the Code sidebar (the same control, so the branch, the comparison, the terminal and the files never disagree), and each option says what the agent changed there and how much is unreviewed, with a count when another repository has unreviewed files. Chats, Decisions and Flow belong to the workspace and stay open when you change repository; a file named as `<repository>/<path>` (the first repository's paths are bare) opens in the right repository. A turn leaves one checkpoint in every repository it changed, each reviewed on its own, and the comparison is remembered per chat and repository. A workspace with chats cannot be deleted. A chat is deleted from the Sessions list (the bin on its row, then Delete to confirm): its messages, pictures, checkpoints, decisions and diagrams go, and the code and git are untouched.
- **Terminal:** retractable real PTY per worktree; in a workspace of several repositories its header says which one.

Files named in the chat are links. A path in the text, in a `code` span or in a markdown link (`src/a.ts`, `a.ts:12`, `a.ts:12-20`, `a.ts:12:5`, `a.ts#L12`, `a.ts#L12-L20`, an absolute path inside a repository, `file://…`) opens in Code, in the repository it belongs to, with the lines marked for a moment. Only files the chat can see are linked (the list is read again when the agent stops), a bare name needs exactly one file with it, and a web link is never turned into a file link. While a reply streams in, the transcript follows it only until you scroll: any move up (wheel, touch, keys, the scrollbar) lets go at once, however slight, and being back at the bottom takes hold again.

Chats belong to a workspace, not to a repository. The sessions list is grouped by workspace, the one on screen first, and choosing a chat of another workspace moves there. Each chat says which repository and branch it runs in.

Dictation turns speech into text on this computer, with Whisper built into the app (whisper.cpp, compiled in, on the GPU through Metal on a Mac; the weights are quantised to 5 bits). The microphone button (or `Ctrl/Cmd + Shift + M`) records. The text is written as you go: when you pause for about 0.45 s the phrase is written after what is in the message field and stays there, and what you are still saying is shown live in the recording bar above the field (the bar also shows the sound, the time, and a line that fills as the quiet nears the 0.75 s that ends the recording by itself, once you have said something; nothing said for 8 s ends it too). Stopping writes what is left, and `Esc` drops only what has not been written yet. A command of your own cannot follow along, so it listens once, to the whole recording, at the end. The recording is made 16 kHz mono in the window and sent to the app as a WAV; it is read from memory and never written to disk or sent anywhere. The first time, the app asks before downloading the model (the small one by default, about 190 MB, once, from huggingface.co; Settings > Voice can choose the larger large-v3-turbo instead, about 574 MB, which is several times slower) into its data folder: the download shows its progress, can be cancelled and picks up where it stopped, and the file is checked (size and header) before it is used. The model is held in memory while dictation is in use and let go of after five minutes without it. Settings > Voice shows whether it is ready, downloads the model, pins the language (detected by default) and can replace the built-in engine with a command of your own (`{file}` is the recording, the text is what it prints).

A `.ipynb` file opens as a notebook: markdown cells rendered, code cells coloured by the editor's tokenizer, and their outputs (text, errors without terminal colour codes, images, markdown, HTML as its text) under them. Nothing is run. The button in the file's header switches to the JSON, which is what is edited and saved.

## Artifacts, privacy and the local API

- Review priority is computed locally from the syntax tree and git. Nothing is sent to a model by itself: decisions are generated only when you press Generate, with the provider and model you pick, and diagrams and BTW questions only when you start them, from a hidden, read-only session.
- Switching a chat to another provider keeps the transcript on screen and writes the whole conversation to `handoffs/<chat id>.txt` in the app data folder, with every entry labelled `[user]`, `[agent]`, `[tool]` or `[subagent: …]`. The first message the new agent receives says that the chat continues an earlier conversation and where the file is, so it can read it if it needs to.
- The agent of a chat is told what Ataraxia is, once per agent process, in the first message it receives (the developer never sees it in the chat). The prompt is short: never generate decisions, flows, comments or priorities on its own; after reviewing or writing code, end with one short question asking whether to generate them; and only once the developer says yes, read the guide at `guide/README.md` in the app data folder. The guide (shipped in `src-tauri/guide/` and rewritten there at every start) says what each artifact is and how to call the local API, in one page per topic (`decisions.md`, `flow.md`, `review.md` and `api.md`), so it is read as a skill is, on demand. Hidden helper sessions (BTW, decisions, analysis) are not told.
- The agent is told to write a TLDR last: after reviewing or changing code, the last thing before its closing question is two to four lines saying what changed, why, and what to check first, so a change can be validated at a glance.
- Tasks are the developer's own list (Tasks, the third screen). A task is a title, optional notes and a status: draft, ready for development, or done. Each has a number that is never reused (`#12`), kept in the `tasks` table. The agent is told, in the first message, to fetch a task the developer names: `GET /v1/tasks/12`, or `GET /v1/tasks?status=ready`, which any token may read; creating and changing tasks is only done in the window.
- Investigation sessions (BTW, discussions, analysis) run read-only: Claude in plan mode, Codex with the `read-only` sandbox, OpenCode in `plan`, and every permission request is refused by the host. A BTW the developer lets edit (the pencil, `Ctrl/Cmd + Enter`, or the "Allow edits" button of a conversation) is a delegated change instead: it runs with the usual permissions, its edits are recorded as a checkpoint of the chat that asked, and the developer approves what it asks to run.
- The local API is plain HTTP on `127.0.0.1`, on a port the system picks, served by the running app. Every agent process of a chat gets `ATARAXIA_API_URL`, `ATARAXIA_API_TOKEN` and `ATARAXIA_SESSION_ID` in its environment, and calls `/v1` from bash with curl, as the guide explains. Requests carry `Authorization: Bearer <token>`. A token is bound to one chat, so a request never names a session, and it is read-write in a normal chat and read-only in a hidden investigation session (a write answers 403). Bodies are JSON, limited to 1 MiB, and there is no CORS. `POST /mcp` is the same server speaking MCP, for the memory tools (see Memory). The endpoints are the ones the old MCP tools were: read artifacts and decisions, open a decision, add a message to it, link a commit, comment on a component or a line, change or reset a priority, and draw a flow. `GET /v1` lists them. Without the variables (the app is not running, or the agent was started outside it) the guide tells the agent to say so and stop.
- `ataraxia --version` prints `ataraxia <version>` and exits without opening a window; the release pipeline uses it to smoke-test every binary.

## Memory

A memory is a note an agent (or you) keeps beyond the chat it came from, and the notes form a graph: each memory is a node and each link between two of them is an edge. It is not tied to a conversation (chats can be deleted and what was learned stays), and Claude Code, Codex and OpenCode read and write the same one.

- **Nodes.** A memory has a title (one line, up to 120 characters), a body (up to 6,000), up to 8 tags, a **kind**, a **scope**, a **source** and an author. The kinds are `semantic` (a fact, a preference, a decision with its reason), `episodic` (what happened: the error, its verified cause, the fix), `procedural` (how to do something, or how the developer wants it done) and `working` (the state of work in progress; it expires after 14 days unless told otherwise, and an expired memory is no longer offered to agents). The scope is global (the developer's own, seen by every workspace) or one workspace (seen by that workspace's chats only); deleting a workspace deletes its memories. The source says who stood behind it: `user` (the developer said it in so many words), `observed` (the agent saw or verified it) or `inferred` (the agent concluded it). An agent may only put a memory in the global scope when its source is `user`.
- **Edges.** A link reads "from <relation> to": `relates_to`, `part_of`, `depends_on`, `caused_by`, `supports`, `contradicts`, `supersedes` or `example_of`. `relates_to` and `contradicts` have no direction, so `a→b` and `b→a` are one link. There can be several links between two memories, each with a different relation.
- **How the agents use it.** Every chat gets an MCP server called `ataraxia`, served by the local API at `POST /mcp` (streamable HTTP, JSON-RPC, stateless) and added to the chat's own MCP configuration with that chat's token, for all three providers. Its tools are `memory_search`, `memory_get`, `memory_create`, `memory_update`, `memory_delete`, `memory_link`, `memory_unlink` and `memory_merge` (which folds several memories into one: the kept one takes the new text, inherits the links of the others, and the others are deleted, all in one transaction). They are real tools, so they cost no `curl` call and, for Claude Code, no permission prompt (the server enforces what a chat may do). The first message of a chat tells the agent to search before a task and whenever the developer mentions something from before, to save what is durable and costly to rediscover (without asking, unlike decisions and flows), to link what is related, and, when results disagree or `memory_create` reports similar memories, to ask the developer which is right and then settle it with `memory_update`, `memory_merge` or `memory_delete`. The server's own `instructions` and the guide page `memory.md` say the rest. Search is local: words in the title, tags and body, with accents and case ignored, titles and tags weighing most, and prefixes matching; it matches words, not meaning.
- **Visibility.** An agent sees the global memories and those of its own workspace, and a chat with no workspace sees only the global ones. A read-only session (BTW, a decision discussion) can search and read but not write; its token is read-only, so a write answers as an error to the model. Every call is in the audit trail (`api_audit`).
- **Guards.** A memory that looks like a credential (a private key, an access token, `password=…`) is refused, with a reason the model can act on. A bad kind, relation, scope or date is an error to the model, not a silent default. If memory is switched off (Settings > Memory), the MCP server is not added to new chats, the tools list is empty and the first message does not mention it.
- **In the app.** The header's graph icon (or `Ctrl/Cmd+Shift+G`) opens the graph: a node per memory (its kind is written on it and drawn as a glyph, and a dashed outline means expired), a line per link with its relation written on it (a conflict, `contradicts`, in amber and dashed; `supersedes` dotted; an arrowhead wherever the relation has a direction; links between the same two memories side by side), filters for kind, scope and expired, a search that dims what does not match, nodes you can drag, and a side panel to read, edit, link, unlink and delete the selected memory or to write a new one. The layout is deterministic (a force layout with no randomness, boxes pushed apart until they do not overlap). Settings > Memory has the same list with a search and filters, and the on/off switch. What an agent writes appears in an open view as it happens.
- **Storage.** The `memories` and `memory_links` tables (migration 016) in the app's database; nothing leaves the machine except what the agent you chose reads.

## Architecture

- **Frontend:** React + HeroUI v3 + Tailwind CSS v4 (`apps/desktop`)
- **Desktop shell:** Tauri 2 (`src-tauri`)
- **Core:** single Rust crate, hexagonal layout (`domain` / `ports` / `app` / `adapters`)
- **Agent connectors:** Orca-shaped ports in Rust
  - OpenCode → ACP
  - Claude Code → custom stream-json (`--permission-prompt-tool stdio`)
  - Codex → custom app-server
  - Provider CLIs are found on `PATH` plus common install dirs; override with `ATARAXIA_OPENCODE_BIN`, `ATARAXIA_CLAUDE_BIN`, `ATARAXIA_CODEX_BIN`
  - Claude Code starts with `--permission-mode auto`; set `ATARAXIA_CLAUDE_PERMISSION_MODE` to another mode (e.g. `acceptEdits`), or to an empty value to use your own Claude settings
  - Agent, model and reasoning effort are set per chat from the composer. The lists come from the live session where the provider reports them (Codex `model/list`, OpenCode ACP config options) and from `.claude/agents` / `.codex/agents` on disk. Claude Code reads them at launch (`--agent`, `--model`, `--effort`), so a change restarts the agent and keeps the transcript; OpenCode and Codex apply them live. Codex has no agent switch in its protocol, so a chosen agent is named in each prompt
  - Subagents show up as a small switcher above the composer. Each one opens as its own conversation, streaming while it works, and the composer there writes to that subagent. Claude relays the message through the main agent's `SendMessage` tool (needs the `agentId` Claude reports when the subagent returns), Codex starts a turn on the subagent's thread, OpenCode prompts its child session. Subagent conversations are kept for the running app, not saved to the database
  - Claude runs most subagents in the background: the call returns at once with an `output_file`, a live transcript of the subagent. Ataraxia follows that file to show its conversation as it works, keeps the subagent open past the turn, and shows the report the main agent gives by itself when it finishes
  - Claude only forwards complete subagent messages (not token deltas); Ataraxia sets `CLAUDE_CODE_FORWARD_SUBAGENT_TEXT` so their text is included
  - Set `ATARAXIA_DEBUG_FRAMES=/path/to/file` to append every raw line exchanged with a provider CLI (`<` from it, `>` to it). It contains the whole conversation, so it is off by default
  - The provider selector in the top bar changes the harness of the open chat. The transcript stays on screen, the whole conversation is written to a text file, and the new agent is told where it is
  - Codex starts with `on-request` approvals, the `workspace-write` sandbox and `approvalsReviewer: auto_review` (a reviewer agent decides eligible requests); set `ATARAXIA_CODEX_APPROVALS_REVIEWER=user` to be asked for everything, or empty to use your own Codex config

## Shortcuts

`?`, or the keyboard button in the header, shows this list in the app. Shortcuts never fire while typing, composing with an IME or editing code.

- `Shift + ↑/↓`: previous/next space, from anywhere, the message field, the editor and the terminal included (the dots on the right edge also follow the mouse wheel while the pointer is over them)
- `Ctrl/Cmd + Shift + B`: go to a branch from a pasted link (Azure DevOps `…/_git/repo?version=GBfeature%2Fx`, GitHub or GitLab `…/tree/x`) or a name, a ref (`refs/heads/x`, `origin/x`) or a `git checkout x` line. A local branch is switched to; one only the remote has is fetched for and checked out tracking it; a link that names a repository of the workspace switches that repository. A pull request link is explained, not guessed at. Git's refusals (local edits, an agent working in the worktree) are shown in the dialog.
- `Ctrl/Cmd + Shift + G`: the memory graph, from anywhere but the editor
- `Ctrl/Cmd + K`: BTW, a side question about what you have open, in any space, run on the model you pick and listed among the chat's subagents (it can also comment, re-prioritise or generate when you ask)
- `Shift + A`: artifacts of the chat (also the layers button in the header, which shows a count when something failed)
- `` Ctrl/Cmd + ` ``: toggle terminal panel (it takes keyboard focus when it opens and gives it back when it closes; its top edge also resizes with the arrow keys)
- Code: `Alt + V` current/previous version, `Alt + Z` wrap lines, `Ctrl/Cmd + S` save, `J/K` next/previous file, `C` comment
- Decisions: `J/K` next/previous decision (in the list they move between rows), `C` jump to the discussion
- Chat: `Enter` send (or queue the message while the agent works), `Ctrl/Cmd + Enter` send now (while the agent works: stop it and put this message first), `Shift + Enter` new line, `Ctrl/Cmd + Shift + M` dictate, `Esc` stop the running turn (or throw a recording away)
- Theme toggle in the header (the same theme in the other mode, light or dark)

When the agent asks for approval while you are in Code, Decisions or Flow, the header says so and takes you back to the chat.

## The animated background

While a chat has no messages, and while no chat is open, the A of ATARAXIA is drawn behind "What shall we build?" as animated ASCII art, on a canvas (`apps/desktop/src/chat/AsciiMark.tsx`; the geometry, brightness and characters are pure functions in `asciiArt.ts`). The stroke breathes slowly, a light climbs the legs and crosses the bar, a faint field of dots drifts around it, and the characters near the cursor light up. It is faint behind the words so they keep their contrast, stops while the window is hidden, is a single still picture with reduced motion (the system's choice is followed while the app is open), and can be turned off in Settings, Appearance, "Animated background" (one choice for the whole app, kept on this computer). The picture is drawn at once and the animation only carries it on: if the system web view stops calling for animation frames while the window is in view, the picture is kept moving on a timer, and a frame that was lost while the Mac slept is asked for again when the window comes back. When the chat gets its first message the A rises and fades within about a second and a half; the drifting field stays, behind the conversation. There it is held to the same faint ceiling as behind the title (so message text keeps its contrast), and shows more strongly only in the margins beside the message column.

## Opening

Opening the app shows animated ASCII art (a piece from ascii-magic, vendored in `apps/desktop/src/vendor/ascii-magic`, drawn as squares) covering the whole window, and the picture depends on the time of day on this computer's clock: a snowy peak above a sea of cloud at sunrise in the morning (05:00 to 11:59), a bright island in the afternoon (12:00 to 17:29), the savanna at sunset in the evening (17:30 to 20:59) and the sea under the moon at night (21:00 to 04:59). It is read once when the opening starts and needs nothing from the network. Only the picture that is needed is loaded. In development, `?time=night` (or `morning`, `afternoon`, `evening`) in the address forces one. The word ATARAXIA is drawn over it, letter by letter, in thin strokes (the A has a crossbar, as in the reference wordmark). After a short hold the letters fade, and the art and the backdrop with them, and the interface that was already rendered underneath is uncovered (about 2.5 s). It plays every time the app opens (any key or click skips it) and never with reduced motion enabled. The letters are paths, not a font: `apps/desktop/src/intro/glyphs.ts` (shapes), `timeline.ts` (timing), `Intro.tsx` (animation) and `AsciiBackground.tsx` (the art). The art library is loaded on demand and never from the network.
